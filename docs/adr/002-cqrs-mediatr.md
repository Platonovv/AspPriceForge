# ADR-002: CQRS-lite через MediatR

## Статус

Принято

## Контекст

Без выделенного слоя приложения вся оркестрация (валидация входа, вызов бизнес-логики, маппинг, cross-cutting:
логирование/кеш) оседает в контроллерах или в «толстых» сервис-классах. Это нарушает SRP: один класс отвечает за
HTTP, и за бизнес-сценарий, и за инфраструктурные мелочи — растёт, плохо тестируется, cross-cutting дублируется.

Плюс у чтения и записи разные потребности: запись держит инварианты и транзакции, чтение хочет проекции и
`AsNoTracking`. Смешивать их в одном сервисе — лишняя связанность.

Альтернатива (логика в контроллерах / общий «сервисный» слой) отвергнута: тяжело тестировать в изоляции от HTTP,
а сквозные заботы пришлось бы прописывать в каждом методе вручную.

## Решение

CQRS-lite: каждый сценарий — это **Command** (запись) или **Query** (чтение) со своим **Handler** (одна ответственность).
Контроллер ничего не оркеструет — он лишь переводит HTTP в запрос и отдаёт его в `ISender.Send(...)` (MediatR).

Cross-cutting вынесен в **pipeline behaviors** (`IPipelineBehavior`): `Validation` → `Logging` → `Caching`. Они
оборачивают КАЖДЫЙ handler в заданном порядке и срабатывают до бизнес-логики — заботы описаны один раз, не в каждом
хендлере.

## Последствия

**Плюсы:**

- Тонкие контроллеры — только трансляция HTTP ↔ запрос, без бизнес-логики.
- Один handler = один сценарий (SRP); чтение и запись разведены и не мешают друг другу.
- Cross-cutting в одном месте: новый behavior добавляется, не трогая хендлеры (OCP), без дублирования (DRY).
- Хендлеры тестируются изолированно, без поднятия HTTP-пайплайна.

**Минусы / цена:**

- Больше классов и непрямота (запрос → MediatR → handler) — выше порог входа в код.
- MediatR как внешняя зависимость в ядре приложения.
- Для тривиального CRUD выглядит избыточно — выбран осознанно ради прод-готовой структуры и единообразия.
