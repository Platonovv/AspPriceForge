# ADR-003: Outbox Pattern для публикации событий

## Статус

Принято

## Контекст

Dual write problem: БД и брокер сообщений — две разные системы без общей транзакции, поэтому атомарно «записать в БД
И опубликовать событие» нельзя. Если упасть между шагами — состояние рассыпается: продукт в БД есть, а событие в брокер
не ушло (потребители о нём не узнают), либо наоборот — событие ушло о том, чего в БД ещё нет.

Альтернатива — публиковать прямо из хендлера сразу после `SaveChanges` — ненадёжна: коммит в БД прошёл точно, а уйдёт
ли сообщение в брокер (доступен ли он, не упал ли процесс между коммитом и публикацией) — гарантии нет. Событие теряется.

## Решение

Бизнес-данные и доменное событие пишем **в одной транзакции**: строка продукта + строка в `outbox_messages` через один
`SaveChanges` одного DbContext → атомарно, оба или ничего.

Отдельный диспетчер (`OutboxDispatcher : BackgroundService`) периодически читает неопубликованные строки
(`WHERE published_at IS NULL`, по порядку `occurred_at` — FIFO), публикует их в брокер через `IEventPublisher` и
проставляет `published_at`. Если брокер был недоступен — событие просто дождётся в таблице следующего прохода.

Гарантия доставки — **at-least-once** (опубликовали, но упали до отметки `published_at` → отправим повторно).
Из этого следует: **консьюмеры обязаны быть идемпотентными** (см. ADR по идемпотентности).

## Последствия

**Плюсы:**

- Атомарность: нет dual-write — событие сохраняется вместе с данными в одной транзакции.
- Переживает падение брокера/процесса: событие ждёт в БД и уйдёт, когда диспетчер снова отработает (eventual delivery).

**Минусы / цена:**

- Не мгновенно: доставка через polling диспетчера → задержка.
- At-least-once → возможны дубли → нужна идемпотентность консьюмера (доп. логика и нагрузка на дедуп).
- Лишняя таблица + фоновый диспетчер: чуть сложнее код и эксплуатация.
