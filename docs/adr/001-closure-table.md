# ADR-001: Closure Table для хранения дерева компонентов

## Статус

Принято

## Контекст

Товар имеет состав (BOM): состоит из компонентов, те — из своих, иерархия произвольной глубины.
Для рекурсивного расчёта цены нужно быстро доставать всю ветку состава — всех потомков узла на любой глубине.

Рассмотренные альтернативы хранения дерева в реляционной БД:

- **Adjacency list** (`parent_id` у каждой строки) — прост на запись, но «все потомки на N уровней» требует
  рекурсивного запроса (recursive CTE) на каждое чтение.
- **Nested sets** (left/right границы) — очень быстрый read, но любая вставка/перемещение пересчитывает границы
  половины дерева.
- **Materialized path** (путь строкой, напр. `1/4/9`) — читаемо, но хрупко при перемещении поддеревьев и завязано
  на парсинг строк.

Профиль нагрузки — read-heavy: дерево меняется редко, а расчёт цены по составу идёт часто.

## Решение

Closure table — отдельная таблица всех пар «предок → потомок» с глубиной: `(ancestor_id, descendant_id, depth)`,
включая связь узла с самим собой (`depth = 0`). Таблица поддерживается при вставке/удалении узлов.

Всех потомков узла достаём одним запросом: `WHERE ancestor_id = X` (всех предков — `WHERE descendant_id = X`),
без рекурсии, на любой глубине.

## Последствия

**Плюсы:**

- Потомки/предки на любой глубине — одним индексированным запросом, без рекурсивного CTE.
- `depth` в строке позволяет ограничивать уровень (например, только прямые дети) без отдельной логики.
- Чтение дешёвое и предсказуемое — под наш read-heavy профиль.

**Минусы / цена:**

- Запись дороже: вставка узла = строка на каждого его предка (пропорционально глубине); перемещение поддерева —
  пересборка набора пар.
- Больше места: число строк растёт как ~`узлы × глубина`.

Осознанный размен: усложняем и удорожаем запись ради дешёвого чтения, что оправдано профилем нагрузки.
