# ADR-004: JWT access + refresh-токены для аутентификации

## Статус

Принято

## Контекст

API должен аутентифицировать запросы и разграничивать доступ по ролям. Два подхода:

- **Серверные сессии** (cookie + session store на сервере): состояние о пользователе живёт на сервере. Минус —
  горизонтальный масштаб требует общего session-store или sticky-sessions; плюс это неудобно для API/SPA/mobile-клиентов.
- **Самодостаточные токены**: состояние несёт сам клиент в подписанном токене, сервер ничего не хранит.

Нам нужна аутентификация, которая масштабируется без общего хранилища сессий и одинаково работает для браузера, SPA и
мобильных клиентов.

## Решение

Два токена:

- **Access** — короткоживущий (~15 мин), **самодостаточный**: claims (включая роли) лежат внутри, подпись проверяется
  по ключу **без обращения к БД** → проверка stateless. В БД не хранится.
- **Refresh** — долгоживущий, **хранится в БД** и ротируется. Нужен, чтобы выдать новый access без повторного логина.

Зачем именно два: короткий access = маленькое окно ущерба при утечке; refresh даёт UX (не логиниться каждые 15 минут)
и, в отличие от access, его можно **отозвать** — он в БД.

## Последствия

**Плюсы:**

- Stateless-проверка access: масштабируемся горизонтально без общего session-store.
- Роли/доступ — из claims токена, без похода в БД на каждый запрос.
- Подходит любому клиенту: браузер, SPA, mobile.

**Минусы / цена:**

- Access нельзя отозвать до истечения (он не в БД). Компромисс: короткий TTL + ротация/отзыв refresh в БД.
- Сложнее серверных сессий: больше движущихся частей (выдача, ротация, валидация).
- Refresh-токены надо хранить и периодически чистить (фоновый `RefreshTokenCleanupService`).
