# ADR-005: Clean Architecture (Domain / Application / Infrastructure / Api)

## Статус

Принято

## Контекст

Хотим, чтобы бизнес-логика не зависела от фреймворков, БД и HTTP: тогда её легко тестировать, а технологии можно
менять, не переписывая логику. Достигается через инверсию зависимостей — ядро объявляет контракты, детали их реализуют.

Без разделения на слои домен прирастает к EF/HTTP: замена технологии превращается в переписывание половины сервера,
тестировать тяжело (всё связано), границы размыты.

Альтернатива — один проект или деление только по техническому типу (контроллеры/сервисы/данные) **без правила
зависимостей** — не спасает: домен всё равно тянет за собой инфраструктуру, связанность остаётся.

## Решение

Четыре проекта (модель «луковицы»):

- **Domain** — сущности, value objects, инварианты. Не зависит ни от чего.
- **Application** — use cases (CQRS) и **интерфейсы** инфраструктуры (контракты потребностей).
- **Infrastructure** — реализации технологий: EF, Redis, SMTP, JWT.
- **Api** — HTTP, middleware, composition root (сборка зависимостей).

**Главное правило:** зависимости текут только ВНУТРЬ, к Domain; Domain не зависит ни от кого, внешние слои — от
внутренних.

Связь с **DIP**: интерфейс живёт в Application (где потребность), реализация — в Infrastructure (где технология).
Поэтому технологию можно подменить, не трогая домен. Пример: `IProductRepository` (Application) ↔ `EfProductRepository`
(Infrastructure).

## Последствия

**Плюсы:**

- Домен изолирован и тестируется без БД/HTTP.
- Технология (БД, кеш, брокер) меняется через реализацию контракта, не затрагивая домен (DIP).
- Чёткие границы ответственности между слоями.

**Минусы / цена:**

- Больше проектов и церемоний (интерфейс + реализация на каждую инфраструктурную потребность).
- Непрямота: чтобы понять путь, надо прыгать между контрактом и реализацией — навигация чуть дольше.
- Для маленького приложения — оверхед; оправдано при росте и сменности технологий.
